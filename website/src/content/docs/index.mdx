## Protect a route in three steps

<p class="landing-lead">Describe your product in one file, start wardn in <code>main</code>, and put <code>Require</code> on your routes. Tables are created for you, typos stop the app at startup, and every denial is explained.</p>

<Tabs>
<TabItem label="1. wardn.yaml">
```yaml
scopes:
  organisation: {}
  branch: { parent: organisation }

permissions:
  customer:view: View customers
  loan:create:   Create loan applications
  loan:approve:  Approve loans

roles:
  org_admin:
    assignable_at: [organisation]
    allow: ["*"]
  teller:
    assignable_at: [branch]
    allow: [customer:view, loan:create]
```
</TabItem>
<TabItem label="2. main.go">
```go
db, _ := sql.Open("pgx", os.Getenv("DATABASE_URL"))

w := wardn.MustNew(wardn.Config{
	File:  "wardn.yaml",
	Store: wardnsql.MustNew(db), // creates its tables on startup
})
```
</TabItem>
<TabItem label="3. routes">
```go
r.Route("/branches/{branchID}", func(r chi.Router) {
	r.Use(w.ScopeFrom("branch", wardn.PathValue("branchID")))
	r.With(w.Require("loan:create")).Post("/loans", createLoan)
	r.With(w.Require("loan:approve")).Post("/loans/{id}/approve", approveLoan)
})
```
</TabItem>
</Tabs>

## Why wardn

<CardGrid>
	<Card title="Your model, not ours" icon="puzzle">
		wardn knows nothing about banks, schools or SaaS. Each product declares its own permissions, roles and scope tree: flat, one level, or as deep as it needs.
	</Card>
	<Card title="Ten minutes to a protected route" icon="rocket">
		One YAML file, one constructor, one middleware. No policy language, no extra server. Mistakes fail at startup with a "did you mean …?".
	</Card>
	<Card title="Secure by default" icon="approve-check">
		Default deny. Deny always wins. Any error means "no". Tenants are isolated. Error responses reveal nothing. None of this can be switched off.
	</Card>
	<Card title="Custom roles, no escalation" icon="seti:lock">
		Let admins create roles at runtime. The escalation guard ensures nobody can grant, edit or remove a role with more power than they hold.
	</Card>
	<Card title="Works with your database" icon="seti:db">
		PostgreSQL, MySQL, MariaDB, SQLite and MongoDB, with automatic migrations. Optional Redis caching across instances that never serves stale access.
	</Card>
	<Card title="Built to be audited" icon="document">
		Every check explains itself. Every change is audited before it happens. A threat model, a security review and a test for every threat ship with the code.
	</Card>
</CardGrid>

## Four ideas, nothing more

<p class="landing-lead">Each idea builds on the one before. Learn these four and you know wardn.</p>

<ol class="ideas not-content">
	<li class="idea">
		<div class="idea-head"><span class="idea-icon"><Icon name="approve-check" /></span><span class="idea-step">1</span></div>
		<h3>Permission</h3>
		<p>An action your code checks.</p>
		<code class="idea-example">loan:approve</code>
	</li>
	<li class="idea">
		<div class="idea-head"><span class="idea-icon"><Icon name="list-format" /></span><span class="idea-step">2</span></div>
		<h3>Role</h3>
		<p>A named set of permissions.</p>
		<code class="idea-example">teller: [customer:view, loan:create]</code>
	</li>
	<li class="idea">
		<div class="idea-head"><span class="idea-icon"><Icon name="code-branch" /></span><span class="idea-step">3</span></div>
		<h3>Scope</h3>
		<p>Where a role applies. Roles flow down the tree.</p>
		<code class="idea-example">organisation › region › branch</code>
	</li>
	<li class="idea">
		<div class="idea-head"><span class="idea-icon"><Icon name="link" /></span><span class="idea-step">4</span></div>
		<h3>Assignment</h3>
		<p>Gives a user a role in a scope, optionally until a set time.</p>
		<code class="idea-example">bayo → teller @ branch:lagos</code>
	</li>
</ol>

<p class="ideas-caption">Put together, in a bank:</p>

```text
organisation:acme                     ada  → org_admin      (everything in Acme)
 └── region:south
      └── branch:lagos                bayo → teller         (this branch only)
                                      tolu → loan_officer   (until Friday)
```

## Choosing the right tool

| | **wardn** | Casbin | OpenFGA / SpiceDB | Home-grown |
|---|---|---|---|---|
| **Built for** | Roles and tenancy inside a Go product | General policy models, in many languages | Sharing individual objects across millions of them (Zanzibar-style) | A product's first few checks |
| **Runs** | Inside your app, on your database | Inside your app | As a separate service | Inside your app |
| **Your team learns** | One YAML file | Casbin's model language | A modelling language and relationship tuples | Nothing new, at first |
| **Tenancy and hierarchy** | Built in | Domains built in; scope trees are yours to build | Built in, as relationships | Yours to build |
| **Admin-created roles that can't escalate** | Built in | Yours to build | Yours to build | Rarely done |
| **Time-limited access** | Built in | Yours to build | Supported | Rarely done |
| **Audit of every change** | Built in, and can block a change | Yours to build | Change history API | Rarely done |

<p class="landing-lead">Different tools for different jobs. wardn is built for roles and tenancy inside a Go product: no extra service, no new language, and the safety rules built in. OpenFGA and SpiceDB are built for sharing individual objects between people and groups at very large scale. They work well together: many products use wardn for who runs what in the organisation, and a relationship service for who can see which document.</p>
